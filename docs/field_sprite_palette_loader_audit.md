## Executive result

The vanilla field engine has five logical paths that load or reload an
object's sprite palette. Every path contains two identical `$18`-byte moves:
one to the primary CGRAM shadow and one to its `$0200`-byte mirror. There are
therefore ten machine-code copy sites.

The destination starts at color 1 of an allocated 16-color OBJ row. A
`$18`-byte move supplies exactly twelve BGR555 colors, so vanilla writes
colors 1-12 and leaves colors 13-15 outside the selected palette record.
Schala's original gameplay art uses all fifteen visible indices. Increasing
one copy length or changing one table entry is not sufficient.

A bounded adapter is feasible without claiming bank `$E4` space:

1. the PC `$07` descriptor resolver gives Schala the per-object palette-source
   key `$FFFF`;
2. all ten six-byte `LDA #$0017 / MVN $7E,$E4` blocks dispatch through one
   common copy resolver;
3. ordinary keys retain the exact `$18`-byte bank-`$E4` behavior;
4. key `$FFFF` copies `$1E` bytes from bytes `$02-$1F` of Schala's named
   expanded 16-color palette allocation.

This preserves row color 0 and fills colors 1-15 exactly through the row
boundary. The adapter is an architecture, not an installed hook. Code
allocation, rejoin-state proof, runtime timing, and transition tests remain
gates.

## Palette-source contract

`verified-static`

The field loader does not dereference a 24-bit palette pointer in each
object. It stores a 16-bit bank-`$E4` source key at `$1400,X`.

| Object family | Descriptor read and multiply | Source-key store |
| --- | --- | --- |
| playable character | `$C0:44C3`, descriptor byte 2 | `$C0:44DD` |
| NPC | `$C0:45CB`, descriptor byte 2 | `$C0:45E5` |
| enemy | `$C0:471A`, descriptor byte 2 | `$C0:4734` |

All three paths multiply one unsigned byte by `$18`. A complete scan of bank
`$C0` finds exactly those three `STA $1400,X` instructions. Consequently:

- ordinary generated keys occupy `$0000-$17E8`;
- `$FFFF` cannot be generated by any vanilla descriptor;
- palette-sharing comparisons at `$C0:71F4/$7291/$7329` can use `$FFFF` as a
  unique Schala source identity without aliasing an ordinary palette;
- multiple field objects representing Schala still share with one another,
  matching the allocator's existing same-source behavior.

For playable descriptors `$00-$06`, palette IDs are `$00-$06`, and the
corresponding rows begin at `$E4:0000,$0018,...,$0090`. Treating descriptor
slot 7 as another PC is invalid: `$E4:F023` is an occupied NPC descriptor,
whose palette byte is `$85`. The unadapted field formula produces source key
`$0C78`, not a Schala palette.

The separate pointer table at `$E4:2A00` also advances in `$18`-byte rows for
the seven PCs, but it does not make entry 7 a playable palette record.

## Exact copy-site matrix

`verified-static`

Each listed pair is:

```text
LDA #$0017
MVN $7E,$E4
```

`MVN` moves `A+1` bytes, so `$0017` means `$18` bytes.

| Logical path | Row calculation | Primary copy | Mirror copy |
| --- | --- | --- | --- |
| event opcode `$33` set palette | `$C0:371E` | `$C0:373D` | `$C0:374A` |
| event opcode `$88` palette restore | `$C0:48DB` | `$C0:48F5` | `$C0:4902` |
| fixed-slot allocator, slots 5-7 | `$C0:71B3` | `$C0:71D3` | `$C0:71E0` |
| general PC/NPC allocator, slots 0-4 | `$C0:7242` | `$C0:7262` | `$C0:726F` |
| restricted allocator, slots 1-3 | `$C0:72DA` | `$C0:72FA` | `$C0:7307` |

Adapting only the general PC/NPC allocator is insufficient. Event-driven
row selection and palette-effect restoration can later replace its output.
Likewise, changing only the first move is insufficient because the field NMI
uploads the mirror buffer.

`Obj_ReclaimSpritePaletteSlot` at `$C0:734C` re-establishes ownership and
sharing links but does not copy colors. Retaining a unique source key is
therefore part of the adapter contract, not merely a dispatch convenience.

## Destination and upload contract

`verified-static`

The five paths normalize a sprite-palette slot into OAM palette attribute bits
and compute:

```text
$7E:2100 + ((palette_attribute & $0E) << 4) + $0002
```

For slot `n`, this is `$7E:2100 + n*$20 + 2`: color 1 of OBJ palette row
`n`. The second move adds `$0200`, selecting the corresponding location under
`$7E:2300`.

| Region | Meaning |
| --- | --- |
| `$7E:2000-$21FF` | primary 256-color CGRAM shadow |
| `$7E:2100-$21FF` | primary OBJ palette rows |
| `$7E:2200-$23FF` | mirror 256-color CGRAM shadow |
| `$7E:2300-$23FF` | mirror OBJ palette rows |

At `$C0:711D`, field initialization mirrors all `$0200` bytes from
`$7E:2000` to `$7E:2200`. At `$C0:712E`, DMA channel 7 uploads all `$0200`
bytes from `$7E:2200` to `$2122` with `CGADD=$00`.

The row consequences are exact:

| Range | Bytes | Vanilla result |
| --- | ---: | --- |
| color 0 | `$02` | not replaced by the object palette loader |
| colors 1-12 | `$18` | loaded from the selected bank-`$E4` row |
| colors 13-15 | `$06` | not supplied by that row |

The last six bytes are not safe implicit colors. Depending on prior shadow
state and palette effects they may be zero, stale, or shared. The supported
Lucca-slot Schala smoke deliberately installed only colors 1-12, and its
runtime render independently corroborates that indices 13-15 do not receive
Schala's intended colors. That runtime diagnostic remains a supported-slot
test; it does not prove this adapter or logical PC `$07`.

## Why the obvious in-place edits are rejected

1. **Changing `$0017` to `$001D` globally is unsafe.** Vanilla source records
   are packed every `$18` bytes, so a 30-byte read consumes the first six
   bytes of the next palette.
2. **Appending one table entry is insufficient.** The field copy bank is
   hardcoded to `$E4`, while no free bank-`$E4` allocation has been proved.
3. **Patching only one allocator misses reloads.** Opcodes `$33` and `$88`
   contain independent copies.
4. **Patching only the primary shadow is transient.** The NMI path uploads
   `$7E:2200`, and normal setup maintains both copies.
5. **Reusing an existing source key corrupts sharing semantics.** The
   allocator treats equal `$1400` keys as the same palette.

## Candidate resolver contract

`proposal`, statically bounded but not installed

### Descriptor boundary

The independent PC `$07` field-descriptor resolver should write:

```text
$1400,X = $FFFF
```

for Schala only. It must leave all vanilla PC, NPC, and enemy keys
byte-for-byte unchanged. `$FFFF` is a source identity, not a ROM address to
be dereferenced by vanilla code.

### Copy boundary

Each of the ten existing six-byte copy blocks can hold a 24-bit `JSL` plus
two padding bytes. All ten calls should target one named expanded-ROM helper
with this logical contract:

| Input | Meaning |
| --- | --- |
| `X` | 16-bit palette source key |
| `Y` | 16-bit destination inside bank `$7E` |
| 16-bit `A/X/Y` | established by every audited caller |

Behavior:

- `X != $FFFF`: reproduce the original `$18`-byte
  `$E4:X -> $7E:Y` copy;
- `X == $FFFF`: read bytes `$02-$1F` from the named `$20`-byte Schala
  gameplay-palette allocation and copy `$1E` bytes to `$7E:Y`;
- never write destination color 0;
- never cross the `$20`-byte destination row;
- preserve the caller's stack discipline and recreate every register, data
  bank, width, and condition-code state consumed after the original `MVN`.

The first call in each logical path is followed by source restoration and a
`+$0200` destination calculation; the second is followed by bank/width
restoration and return. The implementation must prove both rejoin shapes,
not assume that a visually correct frame is enough.

The helper may bind only to a named allocation produced by the deterministic
ROM scaffold. A zero run or an unclassified bank-`$E4` range is not an
allocation.

## Installation and runtime gates

Before this architecture can become `verified-runtime`:

- allocate the helper and the `$20`-byte Schala palette through the
  deterministic expanded-ROM manifest;
- prove all ten hook signatures immediately before installation;
- unit-test vanilla `$18`-byte output and Schala `$1E`-byte output, including
  row guards and both shadow destinations;
- prove register, stack, data-bank, and processor-width equivalence at all
  five logical rejoins;
- run fresh field initialization after Continue/load;
- exercise ordinary PC/NPC sharing, all eight palette slots, hide/reactivate
  reclaim, opcode `$33`, and opcode `$88` restore;
- compare indices 1-15 against the compiler palette and verify indices 13-15
  specifically;
- confirm vanilla PCs `$00-$06`, NPCs, and enemies remain visually and
  byte-for-byte unchanged at the shadow boundary;
- repeat field transitions, battle return, menu return, save/load, and soft
  reset in the required emulator matrix.

Battle, menu walking sprites, overworld sprites, and portraits have separate
palette paths. Passing this field adapter does not promote any of those
surfaces.
